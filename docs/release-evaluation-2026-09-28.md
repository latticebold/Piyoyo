# Piyoyo 0.2.0 リリース評価

評価日：2026年9月28日。
対象：公開前の開発用リポジトリにあった Piyoyo 0.2.0 の `main`。
評価開始時の作業ツリーに変更はなかった。

**初回判定（修正前）：正式リリースは見送り。**
通常操作を対象にしたテストは成功しているが、実行側プロセスの異常終了と、スニペット挿入による既存コードの破損を再現した。
これらは主要機能に直接関係するため、配布文書が整っていても正式版としては合格にできない。
以下の初回評価は上記コミットを対象とする。
その後の修正と検証は末尾の「修正後の検証記録」に記載した。

## 評価基準と結果

想定する配布形態は、Windows利用者向けのGitHub Releases経由のVSIX配布とする。
Marketplace公開、macOS/Linux対応、1.0.0というバージョン番号は必須条件にしない。
「正式」は、明示した対応環境で主要機能と失敗時の挙動を検証し、利用者が取得できる版として扱う。

必須条件がすべて合格なら正式リリース可、再現した不具合があれば不合格、証拠が不足する場合は未確認とする。
点数の合計で重大な不具合を相殺しない。

| 必須条件 | 合格条件 | 結果 | 根拠 |
| --- | --- | --- | --- |
| 主要機能の正確性 | 実行結果が壊れず、自動importが正常なコードを壊さない | 不合格 | UTF-8出力の破損と、自動importによる構文エラーを再現 |
| 異常時の安定性 | 入出力の失敗でホストを終了させず、出力量を制御する | 不合格 | stdin書き込みの未処理エラー、出力上限なし |
| 実行時間の制御 | タイムアウト後に処理を停止し、結果を返せる | 不合格 | 子プロセスがパイプを保持すると制限時間を超えて待つ |
| 自動検証 | テストと構文確認が成功し、重大な失敗条件を検証する | 一部合格 | 117件成功、構文確認成功。ただし今回の再現条件は未網羅 |
| 配布物の整合性 | バージョン、コード、必要な利用者向け資材が一致する | 合格（手元の候補） | 0.2.0 VSIX内のコードとmanifest計14ファイルがSHA-256一致。利用ガイド、画像、ロゴ、LICENSEを同梱 |
| 最終版の実機確認 | 分離したVS Codeで実行、挿入、設定保存、エラー表示を確認する | 未確認 | 0.2.0の記録にはインストール成功まである。主要操作の再確認は記録がなく、今回もUI検証していない |
| 利用手順と対応範囲 | 導入、設定、更新、制限を利用者が理解できる | 合格 | Windows確認済み、他OS未検証、保存済みファイル実行、手動更新を明記 |
| 配布先の準備 | 対象者が正しいタグとVSIXを取得できる状態を準備する | 未完了 | リポジトリはprivate。Releaseは0.1.0の下書きのみで、Assetsも0.1.0 |

## 正式版の前に修正する問題

P1はホストの安定性や既存コードを壊す問題、P2は条件によって機能や制御が破綻する問題として分類する。
ここに挙げたP2も、実行ツールとしての基本保証に関係するため正式版の前に修正する。

### 1. 標準入力の書き込みエラーを処理していない（P1）

対象：`src/runners/pythonRunner.js:245`。

入力を読まずに即終了するPythonへ10MiBの標準入力を渡すと、`child.stdin.end(input)`に対して `write EOF` が発生した。
stdinストリームにerrorハンドラーがないため、独立したNodeプロセスは `Unhandled 'error' event` により終了コード1で終了した。
実際の拡張ホスト終了はUI上では試していないが、この関数は拡張ホスト内で呼ばれるため、ホストの安定性を損なう。

書き込み失敗を捕捉し、早期終了の場合の実行結果を返す必要がある。
大量入力、入力を読まないプログラム、起動失敗を別プロセスで回帰検証する。

### 2. 自動importが複数行importを壊す（P1）

対象：`src/pythonImportInsertion.js:151`、future importでは78行。

次の正常なソースに、`from math import isqrt`を必要とするスニペットを挿入する。

```python
from math import (
    gcd,
)
print(1)
```

挿入位置は1行目の次と判定され、以下のように既存importの括弧の中へ新しい文が入る。

```python
from math import (
from math import isqrt

    gcd,
)
print(1)
```

括弧形式とバックスラッシュ継続の文末を認識し、安全な位置へ追加する必要がある。
対応できない構文では、既存コードを壊す編集を行わず利用者に伝える方法もある。

### 3. 末尾改行なしのヘッダーを壊す（P1）

対象：`src/pythonImportInsertion.js:20`。

ソースが末尾改行なしの `from __future__ import annotations` だけの場合、計算した挿入位置を最終行先頭へ切り詰める。
その結果、通常importがfuture importより前に入り、構文エラーになる。
末尾改行なしの複数行docstringだけのファイルでは、importを閉じ引用符の前に追加し、実行されない文字列内容にしてしまう。

文末へ改行を追加してから必要なimportを置くなど、ヘッダーの後ろという条件を維持する必要がある。

### 4. docstring内のimportを実行文と誤認する（P2）

対象：`src/pythonImportInsertion.js:86`。

次のソースでは、文字列の中の `from math import gcd` を既存importと判断する。

```python
"""
from math import gcd
"""
print(1)
```

gcdを必要とするスニペットに対して追加importを省略し、挿入後のコードでNameErrorになる。
importの検出にも文字列の文脈を考慮する必要がある。

### 5. 子プロセスが残るとタイムアウト結果が遅れる（P2）

対象：`src/runners/pythonRunner.js:183`、224行。

```python
import subprocess
import sys
import time
subprocess.Popen([sys.executable, '-c', 'import time; time.sleep(2)'])
time.sleep(10)
```

制限100msでも実測約2094msかかった。
停止するのは親プロセスだけで、結果を返す処理はcloseイベントを待つ。
子が出力パイプを保持しているため、親の停止だけでは完了しない。
無期限にパイプを保持する子では、結果が返らない可能性がある。
無限に残る子を作る実験は実施していない。

対応OSで子孫プロセスも停止できる処理と、停止失敗時にも結果を返す処理を検証する必要がある。

### 6. 出力サイズを制限していない（P2）

対象：`src/runners/pythonRunner.js:175`、195行。

32MiBの出力を100ms以内に取得し、実験用NodeのRSSは37.4MBから90.4MBへ増加した。
出力全文を文字列として保持し、その後Webviewへ転送して表示する。
無限printなどでは5秒の時間制限に達する前に大量のメモリを使う可能性がある。
OOMやVS Code停止そのものは実験していない。

stdoutとstderrに合計バイト数の上限を設け、超過時に停止し、出力を省略した理由を表示する必要がある。

### 7. UTF-8がチャンク境界で壊れる（P2）

対象：`src/runners/pythonRunner.js:196`、200行。

```python
import os
import time
b = 'あ'.encode('utf-8')
os.write(1, b[:1])
time.sleep(0.1)
os.write(1, b[1:])
```

終了コード0でも、取得結果は `あ` ではなく `���` になった。
各Bufferを個別にtoStringしており、複数バイト文字の途中で分割された状態を次のチャンクへ持ち越さない。
StringDecoderまたはストリームの文字コード設定を使い、stdoutとstderrの両方を修正する必要がある。

## 検証できたことと限界

- `npm test`：117件成功、失敗0、skip0。
- `npm run check`：対象JavaScriptの構文確認に成功。
- `git diff --check`：評価開始時に問題なし。
- 既存 `dist/piyoyo-0.2.0.vsix`：27エントリー。コードとmanifest計14ファイルが現在のHEADと一致。
- GitHub API：現在のmain、Release下書きとAssets、未解決Issueを取得。Actions実行一覧は空。
- 日本語エラー説明に関するIssueが開いたまま。未解決表示だけで不具合と断定せず、現在の実装との対応を整理する。

既存テストには実Pythonを使った実行確認も含まれる。
一方、Webviewの多くは生成HTMLの文字列確認で、VS Code上の実操作を統合して検証するものではない。
テスト件数の多さだけでは今回の不具合を検出できない。
この評価では最新版のUI操作、VS Code 1.90での互換性、macOS/Linux、全履歴の機密情報調査は実施していない。
スニペット96件の本体と設定正規化では、今回のレビューで上記以外の明確な不具合は見つからなかったが、全組合せの実行を保証しない。

## 再判定の条件

1. 上記7件を修正し、各再現条件を対象とする回帰検証に成功する。
2. 最終コミットからVSIXを作成し、コード、バージョン、必要な資材を再確認する。
3. 分離したWindowsのVS Codeで、入力`3 5`から出力`8`、自動import付き挿入、設定の再読み込み後保持、日本語エラーと原文切替、タイムアウトを確認する。
4. `^1.90.0`を維持するなら最低対応版でも主要操作を確認し、難しい場合は検証した最低版に合わせて要件を見直す。
5. 0.2.0のタグと最終コミットに対応するVSIXをRelease下書きへ用意し、変更点と既知の制限を記載する。
6. 一般公開なら、リポジトリ履歴の公開可否とアクセス設定を確認する。privateを維持するなら配布対象者のアクセス権を確認する。

CIによるテスト実行、日本語エラー説明に関するIssueの整理、変更履歴の独立ファイル化は保守のため推奨するが、それらの欠如だけを今回の不合格理由にはしない。
現状は開発中または不具合を説明した限定検証用として扱い、上記条件を満たした時点で正式版を再判定する。

## 修正後の検証記録

2026年9月28日、ユーザーの指示に基づき、7件それぞれをSol（medium）の担当へ割り当てて修正し、親エージェントが統合して検証した。
バージョンは未公開の0.2.0を維持した。

| 初回の指摘 | 修正内容 | 回帰検証 |
| --- | --- | --- |
| 1. stdin未処理エラー | 非同期errorと同期例外を捕捉。通常の早期終了ではPythonの終了結果を保持 | 独立Nodeホストへ10MiB入力を渡し、生存と終了結果を確認 |
| 2. 複数行importの破損 | 括弧とバックスラッシュ継続を論理文として読み、文末の後へ追加 | 挿入後のソースを実Pythonでcompile |
| 3. 末尾改行なしヘッダーの破損 | 最終行末のcharacterを編集位置へ伝え、改行してから追加 | future、docstring、shebang、CRLFなど11種と実際の編集位置を確認 |
| 4. 文字列内importの誤認 | 論理文から実importを検出。docstringの引用符とescapeを順に読む | 文字列内の偽import、実import、docstring保持と名前の使用を確認 |
| 5. 子プロセスによる完了遅延 | Windowsはtaskkillのtree停止、POSIXはプロセスグループ停止。750msの停止待機後も閉じない場合は待機を打ち切る | 実Pythonの子停止、親が終了済みのケース、停止コマンド失敗を確認 |
| 6. 出力の無制限保持 | stdoutとstderrの合計を原文1MiBに制限。超過時は停止して省略理由を表示 | 合計32MiBを出そうとする実Pythonを停止し、保持上限を確認 |
| 7. UTF-8境界の文字化け | stdoutとstderrに別々のStringDecoderを使用 | 1バイトずつの分割、実os.write、probe、EOFと上限境界を確認 |

追加レビューで、docstringとfuture importを同一行に書いた場合の位置計算も修正した。
導入途中の正規表現にはbackslashが多い入力で処理が長時間停止する問題を再現したため、線形時間の走査へ置き換え、独立Nodeホストの時間制限付き回帰テストを追加した。
CPythonとPyPyで元のソースの構文許可条件が異なるケースは、元から構文エラーのソースを変更後の破損と誤判定しないよう、変更前のcompileを確認してから比較する。

- CPython 3.14.6：`npm test` 173件成功、失敗0、skip0。
- PyPy 3.11.11 / PyPy 7.3.18：`npm test` 173件成功、失敗0、skip0。
- `npm run check`：追加した3モジュールを含め構文確認成功。
- `git diff --check`：成功。
- vsce 3.9.2で `dist/piyoyo-0.2.0-verified.vsix` を作成。
- VSIX内のコードとmanifest計17ファイルは、修正後のローカルソースとSHA-256で一致。
- VSIXは30エントリー。テスト、検証用フォルダ、評価書、配布担当者向け資料の混入なし。
- 分離したVS Codeの拡張機能フォルダへのCLIインストールが成功し、`local.piyoyo@0.2.0`を確認。

検証VSIXのSHA-256：`F15C73824C6D4FAF48F2C7BAC07D69F46339D670A9EF74C8A6BC354EB05C0B1F`。
Windowsのサンドボックス内ではtaskkillがアクセス拒否になったため、実子の停止検証と最終全テストはサンドボックス制限外で、テスト自身が起動したプロセスだけを対象に実施した。

Windowsで親が既に終了している場合や停止コマンドが失敗する場合、子孫プロセスの停止を保証できない。
その場合は `processTerminationIncomplete: true` を返し、日本語の説明に「子プロセスの停止を確認できないため、結果の待機を打ち切りました。」と表示する。
PIDを再利用した無関係なプロセスを停止しないため、終了済みの親PIDから曖昧に子を推定して停止する処理は追加していない。

この修正で、初回評価の7件の再現条件に対するコード修正と回帰検証を完了した。
今回確認したVS Code操作はCLIインストールまでであり、最終版のUI操作、最低対応VS Code 1.90、macOS/Linux、Releaseの公開とアクセス設定は別途確認が必要である。
